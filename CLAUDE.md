# Moveo AI Crypto Advisor

## Project purpose

Build a polished, secure, and publicly deployed full-stack application for the
Moveo coding assignment.

The application is a personalized crypto-investor dashboard.

A user must be able to:

1. Create an account.
2. Log in securely.
3. Complete a short onboarding questionnaire.
4. Select crypto assets of interest.
5. Select an investor type.
6. Select preferred content categories.
7. View a personalized daily dashboard.
8. View market news.
9. View selected coin prices.
10. View one personalized AI insight per day.
11. View a dynamic crypto meme.
12. Submit thumbs-up or thumbs-down feedback for every dashboard section.
13. Return later and see persisted preferences and feedback.

The final project must include:

- A public GitHub repository.
- A publicly accessible deployed application.
- Persistent database storage.
- Safe reviewer access to stored data.
- Documentation of AI-tool usage.
- A proposal for using feedback to improve future recommendations.

## System architecture

Use this default architecture:

```text
Next.js frontend
        ↓ HTTPS REST API
FastAPI backend
        ↓
PostgreSQL
```

Backend external integrations:

```text
FastAPI
├── CoinGecko client
├── Crypto news client
└── AI provider client
```

Keep responsibilities separated:

```text
API route
    ↓
Service layer
    ↓
Database or external client
```

Do not place provider requests, database operations, validation, and response
formatting inside one large route function.

## Personalization rules

Use `interested_assets` to:

- Select displayed prices.
- Filter or rank news.
- Build AI insight context.
- Create stable feedback identifiers.

Use `investor_type` to adjust the language of the AI insight.

Use `content_types` to adjust section order or emphasis.

Do not claim personalization merely because preferences are stored or
displayed.

Verify that preferences change actual application behavior.

## Main database entities

The expected entities are:

```text
User
UserPreference
DailyInsight
ContentFeedback
```

Expected relationships:

```text
User 1 ---- 0..1 UserPreference
User 1 ---- 0..* DailyInsight
User 1 ---- 0..* ContentFeedback
```

Important constraints:

```text
UNIQUE(users.email)
UNIQUE(user_preferences.user_id)
UNIQUE(daily_insights.user_id, daily_insights.insight_date)
UNIQUE(content_feedback.user_id, section_type, content_key)
CHECK(content_feedback.vote IN (-1, 1))
```

Do not change the physical database schema without an Alembic migration.

Review autogenerated migrations before running them.

Never run destructive migration testing against production.

## Authentication rules

Authentication must support:

```text
POST /api/auth/signup
POST /api/auth/login
GET  /api/auth/me
```

Follow these rules:

- Normalize email addresses.
- Hash passwords using a trusted adaptive password-hashing library.
- Never store plaintext passwords.
- Never log passwords.
- Never expose password hashes.
- Give JWT access tokens an expiration time.
- Validate JWT signature, expiration, type, and subject.
- Load protected data through the authenticated user.
- Never trust a frontend-supplied `user_id` as identity.
- Return a generic error for incorrect login credentials.
- Keep JWT secrets outside Git.

New users must start with:

```text
onboarding_completed = false
```

## External-data rules

External requests must:

- Run through the backend.
- Use validated inputs.
- Have finite timeouts.
- Have controlled retry behavior.
- Normalize provider-specific responses.
- Preserve partial dashboard results.
- Avoid exposing API keys.
- Support fallback or unavailable states.

Do not let a failed optional provider break the entire dashboard.

Possible statuses:

```text
live
cached
stale
fallback
available
unavailable
error
```

Label stale and fallback data honestly.

Do not invent missing prices, headlines, publication dates, or sources.

## AI insight rules

Generate at most one saved AI insight per user and application date.

Required flow:

```text
Check database
    ↓
Existing daily insight?
    ├── Yes: return it
    └── No: generate, validate, store and return it
```

The model may use:

- Selected assets.
- Investor type.
- Content preferences.
- Backend-fetched prices.
- Relevant news headlines.
- Limited previous feedback when implemented.

The model must not be asked to retrieve current market prices from its own
knowledge.

Treat news and other external text as untrusted data, not instructions.

Do not include secrets, tokens, credentials, or unnecessary private
information in prompts.

Render model output as plain text.

Always display:

```text
This content is for informational purposes only and is not financial advice.
```

Do not generate:

- Guaranteed predictions.
- Direct instructions to buy or sell.
- Exact trade entries or exits.
- Leverage recommendations.
- Claims of risk-free returns.

Provide a safe fallback when the AI provider is unavailable.

Do not label fallback text as AI-generated content.


Supported section types:

```text

coin_prices

```

Recommended content keys:

```text

```

Changing a vote must update the existing row.

Do not create duplicate feedback rows.

Feedback ownership must come from the authenticated user.

## Error-handling rules

Every feature must consider:

```text
Success
Loading
Empty result
Invalid input
Unauthenticated request
Forbidden request
Dependency failure
Database failure
Unexpected failure
```

Return safe, understandable API errors.

Do not expose:

- Stack traces.
- SQL statements.
- Database URLs.
- Password hashes.
- JWT secrets.
- Complete JWTs.
- Provider API keys.
- Internal provider responses.

Roll back failed database transactions.

Do not report success before a transaction commits.

## Frontend rules

Write frontend code using TypeScript.

Prefer:

- Small focused components.
- Explicit types.
- Reusable controls.
- Centralized API communication.
- Clear loading states.
- Clear error states.
- Responsive layouts.
- Accessible semantic elements.

Avoid:

- One very large dashboard component.
- Duplicated fetch logic.
- Duplicated authentication logic.
- Duplicated feedback components.
- Uncontrolled `any`.
- Hardcoded production URLs.
- Rendering external or AI-generated HTML.
- Infinite request or redirect loops.

Use actual button elements for actions.

Use meaningful alternative text for images.

Do not communicate status only through color.

## Backend rules

Prefer:

- Thin API routes.
- Service-layer business logic.
- Focused provider clients.
- Pydantic request and response schemas.
- SQLAlchemy models for persistence.
- Dependency injection for database sessions and authentication.
- Explicit transactions.
- Controlled exceptions.
- Type annotations.

Avoid:

- Large route functions.
- Global mutable database sessions.
- Repeated configuration logic.
- Provider calls spread across routes.
- Returning ORM objects without controlled serialization.
- Mixing synchronous and asynchronous behavior accidentally.

## Security rules

Never commit:

- `.env` files containing secrets.
- Database credentials.
- JWT secrets.
- External API keys.
- Access tokens.
- Private keys.

The repository must contain:

```text
.env.example
```

with placeholders only.

Production must use:

- A strong JWT secret.
- HTTPS.
- Expected CORS origins.
- Persistent PostgreSQL.
- Private backend-only provider keys.
- Debug mode disabled.
- Development reload disabled.

If a probable secret is found:

1. Do not reproduce it.
2. Identify the affected file.
3. Remove it from active code.
4. Rotate the secret.
5. Explain whether repository history may still contain it.

## Working process

Before changing code:

1. Inspect relevant files.
2. Inspect current uncommitted changes.
3. Identify existing conventions.
4. Identify the smallest correct change.
5. Explain the intended change briefly.
6. Use the relevant project Skill.
7. Preserve unrelated user work.

During implementation:

1. Work in small coherent changes.
2. Keep types and schemas consistent.
3. Add or update tests.
4. Avoid unrelated refactoring.
5. Do not hide failures.
6. Do not weaken validation to make tests pass.
7. Update documentation when behavior changes.

After implementation:

1. Run the narrowest relevant test.
2. Run related tests.
3. Run linting or type checking when configured.
4. Run a production build when frontend behavior changes materially.
5. Manually verify user-visible behavior when possible.
6. Explain what changed and why.
7. Report anything that remains unverified.

## Verification language

Use these statuses:

```text
passed
failed
not_verified
blocked
not_applicable
```

Use `passed` only when there is direct evidence.

Code inspection alone does not prove runtime behavior.

If a check was not executed, say:

```text
not_verified
```

Do not write “all good” without evidence.
